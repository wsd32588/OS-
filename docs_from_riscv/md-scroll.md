# 轻量级命令执行器：设计与实施规范

**版本：** v0.1.2（讨论整理稿 / MVP 实施基线，明确数字退出与数值传递）  
**日期：** 2026-10-08  
**定位：** 面向原生 CLI 工具的轻量级、可组合、可优化的命令执行环境  
**文档用途：** 约束第一版实现，记录边界条件与待决事项，防止开发中功能蔓延。

> **阅读约定**：**[确定]** 为讨论中已明确的原则；**[暂定]** 为便于开工提出的实施约定，编码前可调整；**[后续]** 不属于两个月 MVP；**[待决]** 需要明确选择，不能当成已确认需求。

## 0. 一页摘要

**项目目标**：以极少的语言核心组织多个外部可执行程序。`()`、`[]`、`{}` 用于区分执行/返回形式，`->` 用于建立显式执行关系；由 C++ 预分析执行链并调度，由 Rust 实现本地高频工具，由 Go 实现远程连接、接收与相关验证。兼顾 Unix 管道的组合性和 PowerShell 对象化的表达力，但不引入厚重的对象运行时与重复转译。

**优先级**：正确执行 > 稳定边界 > 可观测性 > 可组合性 > 测量后的性能优化。性能是设计约束，不是跳过安全校验的理由。

**两个月交付物**：一个可用的 C++ 命令入口、最小语法解析器与执行计划、Rust 本地工具集、Go 远程工具原型、标准流连接、错误传播、测试及构建脚本。

**明确不做**：完整 Bash/PowerShell 兼容；通用解释型语言；变量、循环、函数、宏系统；复杂对象反射；自动优化任意第三方可执行文件；承诺零拷贝。

## 1. 设计原则与非目标

### 1.1 已确定原则

- **[确定] 语法简单且严格**：核心保留括号构造、执行块及连接符，不为每个工具增加 Shell 关键字。
- **[确定] 工具外置**：查找可执行文件并传入参数；参数是否合法主要由目标工具负责。使用者可用任意语言自行编写新工具。
- **[确定] 多命令执行块**：单个括号块内可以组织不止一条命令；块是组合和分析的基本单位。
- **[确定] 显式链路**：`->` 连接后续执行目标；是否传递数据由返回形式与下游需求决定，不能直接等同于 Bash 的 `|`。
- **[确定] 退出码专用语法**：`[]` 一般不接收裸数字；链尾 `-> [N]` 中的数字专门表示退出码，如 `-> [0]`、`-> [1]`。
- **[确定] 数值数据走 `{}`**：需要向后续执行块传递数字时写 `{42}`，不借用 `[42]`；连接阶段根据消费端契约做必要的数值类型转换。
- **[确定] 全链预分析**：C++ 在启动前解析完整链路，规划执行顺序、连接方式、可提前完成的检查以及返回值需求。
- **[确定] 高性能、少转换**：底层尽可能直接处理字节和原生数据；避免为了对象语义反复包装、序列化和分配。
- **[确定] 有选择地融合**：高频紧密协作的本地操作可以融合；不要把每个语法块强制映射为独立进程。
- **[确定] 职责划分**：C++ 负责控制与计划；Rust 主攻本地类 Unix 工具；Go 主攻网络连接与接收侧验证。
- **[确定] 不追求 PowerShell 式大运行时**：可以借鉴结构化返回，不照搬它的对象管道成本。

### 1.2 非目标与约束

- **[确定]** 不需要 Shell 理解 `find`、`git` 或第三方 CLI 的私有参数。
- **[暂定]** 不进行变量替换、通配符展开、命令替换、内建表达式求值；参数原样交给目标程序。
- **[暂定]** 默认只执行配置目录与允许的 `PATH` 中找到的程序；不把一段参数字符串交给 Bash 再解释。
- **[后续]** GUI、交互式补全、脚本调试器、并行 DAG、插件市场与跨机分布式编排。

## 2. 三语言职责与进程边界

| 子系统 | 技术选择 | 核心职责 | 不应承担 |
|---|---|---|---|
| 控制平面 | C++ | Lexer/Parser、AST、静态规划、命令解析、启动/取消、退出状态与资源回收 | 热路径逐条处理文件或转码中间数据 |
| 本地数据平面 | Rust | 遍历、查找、过滤、文本处理、批量/流式本地操作 | 管理所有第三方 CLI 的命令语法 |
| 远程数据平面 | Go | SSH/连接、远程执行与传输、接收时校验、限额、完整性确认 | 依赖 C++ 对外部输入做最终授权 |
| 操作系统 | POSIX / Windows API | 子进程、pipe、文件描述符/句柄、I/O 背压 | 理解项目的业务对象 |

**[确定] 数据通路原则**：`Rust stdout → OS pipe → Go stdin/其他消费者`；C++ 创建、连接、监控进程与通道，不做逐条对象中转。独立工具必须可以不经管理器单独运行。

**[暂定] 进程边界**：外部普通 CLI 独立进程；可融合的自有 Rust 命令在同一 Rust 执行器内部处理；Go 可采用单独可执行程序。**不在 MVP 中**把 Go、Rust、C++ 的不同运行时强行嵌入同一进程。

## 3. 语法契约

### 3.1 核心符号

| 符号 | 已确认的含义 | MVP 工作假设（尚未最终拍板） |
|---|---|---|
| `()` | 执行块、允许组合多条命令 | 操作型块：只向下游提供完成/失败状态，不默认输出数据 |
| `[]` | **[确定] 不直接承载裸数字数据**；`[N]` 保留给退出状态 | 普通 `[]` 块仍可暂按流式输出理解；纯数字不得当作序列数据传递 |
| `{}` | **[确定] 可表示需要传递的数字**，并支持结构化内容与树形嵌套 | `{42}` 是数值结果，消费端根据约定转换；其他结构形式暂定 |
| `->` | 显式连接后续目标 | 表示有序依赖；有返回值且下游需要时才创建传输通道 |
| `-> [N]` | **[确定]** 显式退出码 | 整个程序链尾的专用 `Exit(N)` 节点；N 为非负十进制整数字面量，不向下游传递数据 |

**[部分确定 / 待决 01]** 已确定 `[]` 不以裸数字作为数据输出、`[N]` 专用于链尾退出、`{数字}` 用于数值返回；`()` 的具体返回契约、普通 `[]` 的流类型、`{}` 的复杂结构类型仍为 MVP 候选，**不能误认为全部定稿**。Parser 应分开标记 `block_kind`、`number_literal` 与 `exit_node`。

**[待决 02]** `->` 是纯顺序关系还是允许上下游流式并行？**[暂定]** 具有顺序依赖语义；当两端协议允许流式消费时，可以并发运行，但必须保持可观察行为和错误传播规则。

### 3.2 示例（意向表达，参数格式由各工具定义）

多命令执行块与顺序执行：

```text
(
    mkdir ./out;
    echo ready
) -> (
    echo finished
)
```

返回序列、流式处理，再生成结构化结果：

```text
[
    rfind ./src --type cpp
] -> [
    rfilter --min-size 4096
] -> {
    rsummary --count --total-size
}
```

链尾显式退出（前序节点全部正常完成后返回指定退出码；`0` 为成功）：

```text
(
    rfind ./src --type cpp
) -> [0]
```

数值传递示例（`{42}` 是数据，不是状态码）：

```text
{42} -> (consume-number)
```

也允许链尾显式非零退出，例如 `(check-condition) -> [1]`；它表示预期执行成功抵达终止节点时返回状态码 `1`。

树形嵌套示意（此处仅演示结构，不承诺具体返回值）：

```text
{
    [ rfind ./src ] -> { rsummary }
}
```

**注意**：`rfind / rfilter / rsummary` 为拟议自有工具名称，不代表当前已实现；`{}` 的实际输出须由原生工具声明或适配器提供。任意外部 CLI 不能仅因被大括号包裹就凭空获得对象语义。

### 3.3 最小语法草案（EBNF 概念版）

```ebnf
program    = chain, { separator, chain }, [ "->", exit_code ] ;
chain      = block, { "->", block } ;
exit_code  = "[", uint_literal, "]" ;
block      = "(", body, ")" | "[", body, "]" | "{", (uint_literal | body), "}" ;
uint_literal = digit, { digit } ;
body      = { command | chain | separator } ;
command   = word, { word } ;
separator = newline | ";" ;
word      = bare_word | single_quoted | double_quoted ;
```

这只是解析目标示意，不是可直接喂给生成器的无歧义正式文法。`[N]` 与一般方括号块存在语法重叠，解析器须优先识别链尾的 `-> [N]` 并保留专用 AST 终止节点。`{42}` 为数字字面量表达式，不应尝试定位名为 `42` 的外部程序。**[待决 03]** 嵌套执行链与命令行的消歧、引号转义、保留符号出现在文件名中的写法，必须在第 1 个里程碑以测试先行冻结。

**[暂定]** 同一块内命令默认按书写顺序运行；块的输出取最后一条命令的输出契约；前面命令的 stdout 默认为普通诊断/终端输出。空块合法但无数据，具体含义由 `block_kind` 决定。

### 3.4 严格范围

- 解析器检查括号配对、合法箭头位置、字符串是否闭合、基本结构。
- 不检查任意外部工具的私有参数，如 `--foo` 是否存在；工具自行报告。
- 语法的特殊符号如 `->`、`[`、`]` 如需作为工具参数，应当被引号或转义保护。
- **[暂定]** 一条 `->` 链中各节点只接收一个直接上游输入。分叉、合并、回环均不在 MVP 内。

### 3.5 链尾退出 `-> [N]` 与数值结果 `{N}`（已确定）

- **括号语义**：`[]` 中单独出现的数字不表示列表元素或待传输数据，而是为退出码保留。`{42}` 表示要传给后续环节的数字值，之后按接收端契约执行必要的类型转换。
- **位置规则（沿用现有 MVP 约束）**：`-> [N]` 只能出现在整个程序最后一个顶层执行链末尾。`[N]` 单独出现、在普通块内部或链中间出现，以及退出节点后再继续连接，均为语法错误。
- **执行语义**：前序所有必需步骤成功完成后，生成 `Exit(N)` 并结束本次执行，设置进程退出状态码为 `N`；不启动名为 `N` 的工具，不创建数值数据，也不给终止节点建立 pipe。
- **失败传播**：前序实际发生的启动失败、非零退出或取消仍按 fail-fast 返回原有错误；正常抵达 `Exit(1)` 后返回非零状态是显式请求，不表示上游失败。
- **转换边界**：`{42}` 仅声明数字数据的意图。转成何种数字类型、是否发生溢出、怎样桥接无元信息的第三方 CLI，依赖消费端契约；不能凭括号自动推断任意外部程序类型。
- **仍待决**：退出码数值范围、负数是否允许、浮点数能否出现在 `{}` 数值表达式中。MVP 文法先只接受非负十进制整数字面量；范围检查需符合目标平台。

```text
合法： (echo ok) -> [0]             # 返回状态码 0
合法： (echo ok) -> [1]             # 返回状态码 1
合法： {42} -> (consume-number)    # 向下游传递数字 42
非法： [42]                        # 数字退出节点缺少 -> 与上游链
非法： (echo ok) -> [0] -> (echo later)
非法： [42] -> (consume-number)    # 不能用 [] 裸数字传递数据
```

## 4. 返回值、输入与错误语义

### 4.1 三种不同的信息

1. **执行状态（必有）**：启动失败、退出码、信号/取消、错误原因；哪怕没有数据返回也必须保留。
2. **数据输出（可无）**：字节流、序列或结构化对象；只有下游使用时才需要传输。
3. **诊断输出（独立）**：stderr、日志和用户提示；不得随意混入类型化数据通道。

`->` 不能把“上一条命令退出码是 0”和“上一条命令返回一个值 0”混为一谈。`-> [N]` 的数字是**最终进程状态**；`{N}` 的数字才是供后续阶段接收和转换的**数据值**。

### 4.2 MVP 约定（暂定）

- `(action)`：保留状态；输出数据默认不连到下游；若命令直接打印内容则显示在当前终端（或由管理器重定向）。
- `[sequence]`：允许通过 stdout/pipe 交付一条字节流；自有工具可声明更具体的元素类型。**`[]` 不表示必须将数据全部放入数组，且 `[42]` 不能表示数值数据**。
- `{value}`：允许数字字面量作为标量返回，例如 `{42}`；依据下游契约做必要的数值转换。结构化对象仍需要自有工具或适配器声明契约，不能靠括号猜测第三方 CLI 的输出。
- 普通第三方 CLI 缺少描述信息时，stdout 视为 `Stream<Byte>`，stderr 保持独立；不进行自动文本→对象转换。
- **[确定] 链尾退出**：检测到 `-> [N]` 时，执行计划追加 `Exit(N)` 终止节点；只有前序成功才抵达该节点，不创建到此节点的数据通道。
- **失败策略**：默认 fail-fast；发生错误时停止启动未开始的依赖节点，取消已运行的有关节点，回收所有句柄并返回明确错误。

### 4.3 可选工具描述（不强制第三方提供）

```json
{
  "name": "rfind",
  "executable": "bin/rfind",
  "input": "none",
  "output": "stream:file_entry",
  "fusion_group": "rust_fs"
}
```

**[暂定]** 采用外部 manifest 或随工具安装的元数据文件；无 manifest 仍可执行。`fusion_group` 只是优化提示，不能确保真的可融合。描述元数据须可信且受版本控制，不能从远程未经验证的数据中盲目信任。

## 5. 执行计划与优化

### 5.1 处理流水线

```text
源代码
  ↓ Lexer（括号/箭头/引号/参数）
AST（Block / Chain / Command / Exit）
  ↓ 语法验证、程序定位、可选契约分析
执行计划 IR（依赖、输入输出、退出策略）
  ↓ 确定 pipe / 顺序边界 / 并发准备 / 可融合阶段
进程启动和执行（C++ 控制，Rust/Go 处理数据）
  ↓ 状态收集、取消、资源回收
结果摘要
```

### 5.2 优化允许与禁止

- **允许**：跳过无消费者的中间数据序列化；合并自有 Rust 热路径中的连续过滤操作；重用缓冲区；将 Go 握手准备与独立本地扫描重叠；粗粒度批量交付。
- **禁止**：仅因无人消费 stdout 就删掉可能有副作用的外部进程；改变文件写入顺序；擅自把任意第三方程序“融合”；因预检查成功而跳过接收端实时授权。
- **注意**：借用和引用本身通常并不昂贵。应优先测量分配、复制、系统调用、进程启动、缓存缺失及跨语言边界成本，再决定哪些模块融合。

### 5.3 基线观测指标

| 指标 | 测量方法 | MVP 标准 |
|---|---|---|
| 冷启动延迟 | 空动作 / 单个外部进程，各测 P50/P95 | 记录基线，不承诺任意阈值 |
| 管道吞吐 | 固定大小字节流，单段与双段链对比 | 不出现不受控内存增长 |
| 文件扫描 | 同数据集比较独立工具与链式工具 | 记录差距并定位热点 |
| 峰值内存 | 大文件/大量文件目录 | 与输入规模不呈无界线性增长（流式路径） |
| 故障恢复 | 断网、异常退出、主动取消 | 无僵尸进程、无悬挂管道 |

## 6. 接收侧验证与安全边界

- **C++ 启动前**：静态语法、括号与引号、命令存在性、声明的契约与连接合法性、启动资源预算。
- **Rust 本地执行时**：路径访问、实际读写权限、文件系统错误、符号链接策略；不重复扫描整个文件树作无意义的预检查。
- **Go 接收时**：身份与授权、数据长度及上限、目标路径合法性、协议版本、分块校验、完整性校验；最终提交前检查成功状态。
- **TOCTOU**：预检查与实际使用之间可能变化；远程写入必须在实际操作前验证权限与边界。
- **进程控制**：不默认通过系统 Shell 拼接命令字符串；Linux 使用 `execve`/`posix_spawn` 路线，Windows 使用 `CreateProcessW` 等原生接口；必须安全处理参数、句柄继承、超时与取消。
- **文件传输**：默认采用临时文件接收，完成校验后再原子性提交（受文件系统条件限制）；异常中断时清理临时文件。

| M5 | 第 8 周 | 文档、自动化测试、构建打包、基线性能测试 | 一键构建；样例和故障测试可重复 |

**范围保护**：如果工期紧，优先保证“C++ + 一个 Rust 工具 + 一个 Go 工具 + `->` 数据流闭环”；延后类型化对象管道与跨命令融合，而不是牺牲安全检查或进程回收。

### 7.3 首批验收用例

- `()`、`[]`、`{}` 的嵌套结构能生成正确树形 AST；未闭合、错配、连续 `->` 必须报错。
- `-> [N]` 只在程序链尾生成 `Exit(N)`；`-> [0]` 与 `-> [1]` 均合法，不能掩盖前序失败；`[42]` 不能作为下游数字输入；`{42}` 应解析为数值数据并支持契约转换。
- 多命令块内按规定顺序执行；仅影响下一块所需的返回数据走管道。
- 未找到工具、权限拒绝、参数错误均能报告原始失败，不崩溃。
- 标准错误与数据通道隔离；空输出、大输出、二进制数据均可处理。
- 管道下游提前退出时，生产者能感知关闭，不会死锁。
- 取消运行中的链后没有残留子进程或开放句柄。
- Go 对网络输入做长度/权限/目标路径检查；校验失败不得提交目标文件。
- Rust/Go 工具即使绕过 C++ 管理器也能独立执行。

## 10. 文档维护规则

1. 每次改变语法，先改 `docs/SYNTAX.md` 的正反例，再改 parser。
2. 每次改变执行/返回语义，更新本规范与 `docs/DECISIONS.md`，加回归测试。
3. “希望未来支持”一律记入后续计划，未经评估不得加入 MVP。
4. 性能优化必须附可复现基准，避免凭感觉合并模块。
5. **版本升级准则**：v0.1 保证基础组合；v0.1.1 补充链尾退出；v0.1.2 明确 `[]` 退出码与 `{}` 数值传递；v0.2 再评估类型化对象流；v0.3 再考虑执行图和融合优化。版本仅表示阶段建议，不对应发布日期。
