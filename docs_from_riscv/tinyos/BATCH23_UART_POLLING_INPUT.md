# BATCH23：UART轮询接收与内核任务回显

日期：2026-11-15。状态：功能、全部既定P0及原三题原答/集中澄清归档完成，本批收尾。

## 1. 目标与范围

在QEMU终端键入字节，由内核读到并回显；没有输入时用户任务、定时器和原文件生命周期继续正常工作。
将现有task_a的无限A输出替换为回显，复用同一个S-mode任务及原任务槽，不添加新任务或改变原两个用户程序。

本批只补UART原始字节接收。PLIC/外部中断、软件输入队列、阻塞等待、用户console接口、标准FD和行编辑在后续分开设计。
不添加临时GETCHAR18，不把既有合法文件fd0改成stdin；不修改OpenFile/Process/调度器来适配尚未引入的设备文件。
task_a是本批唯一RX消费者，UART驱动只提供硬件操作；以后接用户console时再明确移交接收职责，不能让两个消费者争抢字节。

## 2. 当前基础与寄存器

当前drivers/uart.c已有轮询发送、字符串和十六进制输出；boot已把0x10000000所在页建立内核恒等映射，用户root借用内核映射。
无需再分配或映射一页，也不需要为此次接收新增初始化流程；沿用当前QEMU/OpenSBI已配置好的串口，DLAB为0。

本机QEMU版本10.2.1。核对相同上游版本的[virt板级映射](https://github.com/qemu/qemu/blob/v10.2.1/hw/riscv/virt.c)
和[16550A串口实现](https://github.com/qemu/qemu/blob/v10.2.1/hw/char/serial.c)：

| 位置 | 含义 | 本次操作 |
| --- | --- | --- |
| base 0x10000000 | UART0 MMIO基址 | 沿用现有常量 |
| offset 5，LSR bit0 | DR，接收数据已就绪 | 判断是否可以读 |
| offset 5，LSR bit5 | THRE，发送保持寄存器空 | 原输出函数继续使用 |
| offset 0，读 | RBR，接收字节 | DR置位后读取一次 |
| offset 0，写 | THR，发送字节 | 原uart_putchar继续使用 |

偏移相同不代表读取和写入做同一件事。DLAB置位时offset0含义会改变，本批不修改LCR/分频/FIFO/中断配置。
读取RBR是有副作用的消费操作；无数据时不能拿一次RBR读取结果当成有效字节，读到0也不能判断为空。
QEMU在FIFO空或单字节被读后清DR；驱动自身不需要手动清该位。

## 3. 作者需要修改的三个位置

### include/drivers/uart.h

在现有extern C保护内添加：

```c
/* 0..255: consumed one byte; -1: no byte available right now. */
int uart_try_getchar(void);
```

返回int而不是char，才可以同时表达全部256种字节与-1。
0x00和0xff都是成功数据；-1是暂时无数据，不是EOF，也不是应终止任务的错误。

### drivers/uart.c

沿用现有UART0_BASE/UART_LSR_OFFSET，新增模块私有常量：

```c
#define UART_RBR_OFFSET 0
#define UART_LSR_DR (1U << 0)
```

实现int uart_try_getchar(void)，算法只有两条路径：

1. 使用现有volatile unsigned char指针访问MMIO，读取一次LSR。DR未置位，立即返回-1，不读取RBR。
2. DR置位，读取一次RBR，将unsigned char值提升为int返回。这次调用只消费一个字节。

接收函数内部不写等待循环、不回显、不分配内存、不操作任务状态；回显属于调用方。
不要先把字节存入可能有符号的char再提升，否则0xff可能与-1混淆。原发送接口保持。

### kernel/boot/private/demo_tasks.c

task_a可在启动时打印一次`[uart] polling echo ready\n`作为提示，随后循环（提示文字不影响接收功能）：

```text
尝试读取一个字节
    暂时无数据 → 调用现有delay，再进行下一轮
    收到0..255 → 使用uart_putchar回显，立即继续尝试读取
```

用int保存结果、先判断是否非负，再明确转换给现有uart_putchar。
只在无数据时delay，不要每收到一个字节都delay，避免积压已有输入。
保留S-mode定时抢占；不添加关中断、wfi或用户态yield包装调用。内核S任务不借用户ecall发起调度。
task_b、boot创建顺序、两个用户程序及原退出码不变；本次没有新增.o，Makefile无需加对象。

### 功能梳理

宿主输入送入UART，硬件用DR告知数据就绪；驱动尝试一次，返回一个原始字节或-1；task_a据此回显或稍后重试。
读取RBR消费输入，驱动不负责命令或文件；回显仍调用原发送路径，之后才可在独立命令层补内核文件查看。
delay本身是忙等，其他任务获得运行机会依靠已有定时抢占；本批尚未引入输入阻塞/唤醒。

## 9. 原三题回答与集中澄清（2026-11-15）

### 作者原答（保留原文）

> 方便处理，因为无法对char进行判断，return -1能直观确定表达没有字符被获取，0x00是0，0xff是返回255,无输入返回-1
>
> THRE是说有没有需要输出的内容，DR是接收队列有没有输入内容，无条件读取RBR可能读取到旧值
>
> 驱动立即返回是防止阻塞队列，task_a反复轮询是等待下一步操作，delay是让出了cpu等待下一次输入

### 集中澄清

1. **三个返回值正确，原因应是表示范围，而非char不能判断。** char可以参与比较；本平台8位字节的256种值全都可能是有效输入，
   还需要一个与它们均不同的“暂时无数据”值。int能同时表达0..255和-1，避免丢失NUL或把0xff与空状态混淆。
2. **DR及旧值风险方向正确，THRE含义需修正。** THRE置位表示发送保持寄存器空，可以写下一个字节，不是在告诉软件有没有待输出内容。
   DR置位表示接收端有字节可读；这里描述硬件接收状态，当前尚无软件输入队列。发送就绪与接收就绪是两个独立条件。
   DLAB为0时，offset0写为THR、读为RBR，访问方向决定含义；无DR仍读RBR可能取到旧值或空FIFO的值，无法把它解释为新输入。
3. **立即返回限制一次调用的工作量；delay没有让出CPU。** 当前没有等待队列，驱动只尝试一次，不在内部等待新数据；
   task_a作为调用者决定反复尝试，属于轮询。delay的实现只是循环执行指令，既没把任务设成BLOCKED，也没主动切换现场。
   其他任务能运行依靠定时器中断进入trap_handler，再调用sched_on_timer抢占；不是delay完成了调度。

### 协作者整理的修正版（非作者重答）

1. int为全部字节值之外的-1保留空间：0x00返回0、0xff返回255、暂空返回-1；char本身可以比较。
2. THRE表示发送端可继续接收一个待发送字节，DR表示接收端有数据可读；同地址读写对应不同逻辑寄存器，须先检查对应就绪位。
3. 驱动一次尝试后立即返回，task_a负责轮询；delay是忙等，实际切换由定时抢占完成。以后阻塞等待需明确等待状态与唤醒机制。
