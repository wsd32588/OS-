## 1. 本批目标与完成边界

B19已经证明用户ELF能够在自己的页表下运行，再通过exit回到内核。
那条路径收到第一次用户trap就结束演示，没有再次恢复用户程序。
本批增加“处理请求→准备返回值→恢复同一个用户程序”，使一段用户调用链能够多次往返。

```text
U：write(只读段缓冲区)
  → S：保存现场，切内核表，读取用户数据，输出
  → 修正现场中的sepc/a0，切用户表，sret
U：检查返回长度，write(跨guard的错误缓冲区)
  → S：完整检查失败，返回-1，零输出
  → 修正现场并恢复U
U：检查-1，write(用户栈缓冲区)
  → S：输出并返回长度，再恢复U
U：检查返回长度，exit(0)
  → S：结束本次演示，恢复Bare/CSR并回收资源
```

固定示例共4次U ecall、3次恢复。exit结束后不再恢复该用户。
旧双应用仍按第三章的Bare调度运行；本批不同时接入分页任务切换、yield或timer抢占。

## 2. 完整路径怎样复用

原paged_user.S已经能完成：

```text
__paged_enter保存内核调用续点
  → 高__paged_restore → 用户表 → sret
  → 用户ecall
  → 高__paged_alltraps保存现场 → 内核表/内核栈
  → 低__paged_return → ret回Rust调用处
```

第一次返回Rust后，用户现场还在同一个物理页里，用户栈和数据也没有被释放。
框架修改一份现场副本、写回现场页，再调用同一__paged_enter，就可以恢复用户暂停处。
每次低入口会重新保存这次内核调用的128字节续点，并更新kernel_sp。

因此不用新增一套寄存器保存汇编。恢复的sepc来自已有现场，不能每轮重置为ELF入口；
其余用户寄存器和用户栈也不能每轮清零或重新初始化。

ActiveRun持续覆盖整个往返循环，内核处理各请求期间保持内核Sv39表。
直到exit结束，才由守卫恢复原Bare和8项CSR，随后释放两个空间及现场页。

## 3. 内核不能把用户VA直接当指针

用户传来的a1只是用户地址空间中的一个地址数值。例如：

```text
用户表：VA 0x40001000 → 某个用户物理数据页
内核表：没有映射VA 0x40001000
```

切回内核表后，直接把这个数转成指针再读，硬件使用的是内核表，不能到达那份用户数据。
临时切回用户表运行普通Rust也不行，因为当前内核代码、栈等并不在那里映射。

本批按用户MemorySet查询该VA的叶权限，找到它对应的自有数据页，再通过内核已有的页池恒等映射读取。
现有owned_byte接收一个用户VirtAddr，定位拥有该VPN的FrameTracker，再读取相应页内偏移。
它不会按那个用户VA直接解引用，也不会在本批转移数据页所有权。

权限与归属都要检查：有一个可访问的物理页，不表示该用户具有读它的权限；
PTE存在也不表示它是这个空间仍持有的自有数据页。
本批要求V、U、R全部存在，拥有者仍存活。写出只需要读用户缓冲区，不要求用户页可写。

## 4. 本批接口约定

| 项目 | 约定 |
| --- | --- |
| 系统调用号 | a7；write=64，exit=93 |
| write参数 | a0=fd，a1=用户VA，a2=字节数 |
| 支持的fd | 仅1 |
| 最大写出长度 | 256字节 |
| write成功 | 返回实际写出的字节数 |
| write失败 | 返回-1，整次零输出 |
| fd=1且长度0 | 成功返回0，不访问或转换缓冲区地址 |
| exit参数 | a0为退出值；本示例应为0 |
| 未知调用号 | 返回-1；只定义兼容分支，不增加本批验收场景 |

对于非空缓冲区，要检查长度上限、地址范围加法溢出、canonical地址、每个涉及地址的权限及拥有者。
全部检查通过后才复制到内核局部缓冲区；全部复制成功后才调用SBI逐字节输出。

本批最多256字节，按字节遍历更容易核对。各页物理位置可以不连续，不能从第一个PA一直越页读取。
循环校验是准备系统调用缓冲区的实现方式，不是新的测试矩阵。

## 5. 三处作者核心

核心集中在新mm/paged_syscall.rs；原B19汇编和三处作者实现保留。
入口接线、上下文快照读写、有限往返驱动、用户样例及最小验收由框架提供。

### A：copy_readable_user

输入为用户MemorySet、起始地址数值和内核目标切片output，长度就是output.len()。

1. 空切片直接Ok，不要求起点能转换为VirtAddr。
2. 非空长度超过MAX_WRITE则Err；用checked_add验证整个半开区间不溢出。
3. 第一遍遍历整个范围：构造VirtAddr，检查leaf_flags包含V|U|R，检查owned_byte存在。
4. 所有地址验证通过后，第二遍读取owned_byte并填入output，最后返回Ok。

这里MAX_WRITE已在本文件定义；VirtAddr位于super::address，PTE_V/PTE_U/PTE_R位于super::page_table。
可按需导入，也可以使用完整模块路径。leaf_flags返回Option<u64>，owned_byte返回Option<u8>。

判断“同时具有这些位”应使用：

```rust
flags & required == required
```

不能只判断其中任意一位非零，也不能要求flags与required完全相等，否则会误拒合法的A/D/W等位。
拒绝发生在第一次修改output之前；不要直接把用户start转换为Rust指针或slice。

### B：dispatch

从保存现场的x[17]取得调用号，x[10]、x[11]、x[12]分别是前三个参数。
按第4节的完整约定处理：

- write：检查fd和长度；创建256字节内核缓冲区；调用A填充所需切片；
  失败返回Outcome::Return(-1)，成功后逐字节输出并返回长度。
- exit：返回Outcome::Exit(退出值)，不进行用户恢复。
- 其他调用号：Outcome::Return(-1)。

Return/Exit是本批内核处理结果的枚举，不是进程状态枚举。
dispatch不修改现场，也不切表；框架根据结果决定恢复还是结束。

### C：prepare_resume

输入为独立的PagedTrapContext副本和系统调用结果：

1. 先计算context.sepc.checked_add(4)，溢出则Err，不先修改任何字段。
2. 将计算结果写入sepc。
3. 将result as usize写入x[10]，返回Ok。

这里的-1以寄存器位模式保存，用户包装按isize读回，得到同一个-1。
只改sepc和返回a0，其他用户寄存器、状态及内核返回路线应保留。
框架负责把完整副本写回现场页，并在所有临时引用结束后再次进入汇编。

三处完成后移除本文件compile_error守卫，再整批验证。
每次write不论成功还是返回-1，都已经处理了这条ecall，恢复时都要跳过它。
exit不调用C，因为本批不会再次执行该用户程序。

## 6. 框架提供了什么

新的syscall_demo ELF与旧image_demo分开构建，继续使用受限三段布局。
保留两页data/BSS与两页用户栈，因此仍为6个用户数据页。
错误缓冲区位于0x40003ffe，前2字节在合法RW页，后2字节进入0x40004000开始的guard。
合法前缀写入QZ，用于观察拒绝时有没有错误输出前缀。

错误指针用原始参数的ecall包装传入，不创建跨未映射guard的Rust切片。
正常用户栈消息则强制放在真实栈中，框架会核对它传入的VA属于用户栈。
这些固定地址只属于本示例的链接布局，不是通用内存分配接口。

所有Rust处理都发生在用户已暂停、内核恒等映射已恢复、SIE和sie均为0时。
现场内容以Copy值快照取出和写回，没有页内引用跨越用户运行或汇编写入。
FrameTracker相关注释会明确此时也允许通过已经核验的内核页池恒等映射访问；不改变分配/回收算法。

## 8. 完成后的三个理解题

1. 内核已经切回自己的页表，为什么不能直接读取用户传来的VA？V/U/R检查与找到数据页拥有者各解决什么问题？
2. 一次write返回-1时，为什么仍需sepc+=4并把-1写入x[10]？下一次恢复为什么不会重新从ELF入口运行？
3. 为什么多次ecall仍只占23页？哪些引用必须在下一次进入用户前结束，为什么本批只在最后恢复Bare并回收？

### 原回答、集中审查与修正版（2026-10-25）

**第1题原答：**

> 发过来的VA不一定合法，而且还需要转化为PA,内核需要通过MMU操作物理内存,VUR检查当前页是否为用户可读的有效页表，所有者检查防止A修改B需要的内容

**审查：**注意到了用户地址的合法性、翻译与权限，但需要明确当前MMU使用的是内核表，
不会自动按用户表解释传入的数值。V/U/R检查针对叶表项及其映射权限，不是证明整张页表有效。
本次write只读取用户缓冲区，所有者检查的直接作用是确认该MemorySet仍持有相应数据页。

**修正版：**切回内核表后，用户VA与内核VA属于不同地址空间，不能把用户传入的地址数值直接当内核指针。
内核依据用户MemorySet检查映射并定位自有物理页，通过当前内核表的页池恒等映射读取对应字节。
V表示表项有效，U表示允许用户访问，R表示允许读取；这些位必须同时存在。
owned_byte检查还要求存在对应VPN的数据页拥有者，使读取落在本空间仍持有的页上。
权限与所有权承担不同职责：前者说明访问是否允许，后者说明页面归属与生命周期；本次不会修改其他用户的数据。

**第2题原答：**

> write返回-1的时候并没有退出，如果不+4就会一直错误跳转，我们已经保存了现场数据，所以到时候直接读取当页数据而不是从ELF入口重新开始

**审查：**没有退出、请求完成后要继续运行的方向正确。
不推进sepc的具体后果是重复执行同一条ecall；恢复执行依靠寄存器与sepc，不是笼统的“读取当页数据”。

**修正版：**-1表示这次请求已经处理但失败，内核仍应让用户取得结果并继续执行。
ecall固定为4字节，保存的sepc指向ecall本身；返回前加4，使sret回到后继指令，避免重复陷入。
把-1的寄存器位模式写入保存的x[10]，恢复汇编将其装入a0，用户包装按isize取得-1。
恢复时使用现有现场中的寄存器和已经推进的sepc，用户栈与程序页也一直保留，因此不会重新装载ELF或从入口开始。

**第3题原答：**

> 因为会回收重复使用，只存有不重要临时脏数据的，最后的不知道

**审查：**需要区分“整批一直保留并复用”与“每次释放后重新申请”。
引用能否跨恢复取决于是否会与用户/汇编对同一内容的访问冲突，与数据是否重要无关。
最后恢复与回收的理由原答尚未覆盖，下面补齐。

**修正版：**11个内核表页、5个用户表页、6个用户数据页与1个现场页在整个循环中持续存活，总计23页。
每次ecall复用已有表、用户栈和现场，不重新分配或回收这23页；三个普通调用后用户都还要继续运行。
指向将由用户或汇编修改的现场页、数据页内容的Rust引用，必须在恢复用户前结束，避免共享/独占引用与后续写入冲突。
独立的Copy现场快照是值，不是对实际现场页的引用；保活资源的所有者和受控借用则继续覆盖硬件使用期。
只有收到exit、不再恢复该应用后，本演示才结束ActiveRun：在低地址内核环境恢复原Bare与CSR并完成地址翻译同步，
随后释放两个根表和数据页，避免硬件继续使用已被回收的页表或数据。
恢复Bare是本批返回原启动环境的安排；长期分页内核也可以切到另一张持续有效的内核表后回收旧空间。

三题已集中讲解。修正版包含协作者补充，不把补充内容计作原答已经独立覆盖；本次只保存答案与进度，不准备下一批。
