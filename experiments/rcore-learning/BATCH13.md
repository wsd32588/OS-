本批只处理 4KiB 页。satp 继续保持 Bare：新建的页表暂时只是一组内存中的数据，

## 2. 模块怎样连起来

```text
heap_allocator：为 Vec 等元数据提供缓冲区
address：VA→VPN、三级索引、页内偏移；PPN→物理页首地址
frame_allocator：分配清零的 4KiB 页，FrameTracker 持有页所有权
page_table：把这些页当作表，读写 PTE，建立映射并遍历查询
mm::init：依次初始化，并在运行应用前完成本批演示
```

页表本身也占物理页。一张表为 4096 字节，每项 PTE 为 8 字节，因此有 512 项。
本批使用两条相邻虚拟页映射，它们共用根表、L1 表和 L0 表：

```text
根表 L2 --indexes[0]--> L1 --indexes[1]--> L0
                                            |--indexes[2]=1--> 第一数据页
                                            |--indexes[2]=2--> 第二数据页
```

因此需要 3 个页表页，加 2 个数据页，共 5 页。更多映射未必都能共用同一条路径。

## 3. PTE 的位布局

```text
 63             54 53                          10 9    8 7          0
+-----------------+------------------------------+------+------------+
| 本批置零         |          PPN：44位             | RSW=0| flags：8位 |
+-----------------+------------------------------+------+------------+
```

这里的高位规则限定在本批未启用相关扩展的基础 Sv39 格式。
PTE 保存页号，PPN 放在 bits[53:10]，所以编码是 `PPN << 10`。
物理页首地址则是 `PPN << 12`：这是两种不同布局，不能混用。

| 位 | 含义 | 本批用法 |
| --- | --- | --- |
| V，bit0 | 表项有效 | 中间项和叶项都需要 |
| R/W/X，bit1/2/3 | 读、写、执行权限 | 叶项至少有 R 或 X；W 要求 R |
| U，bit4 | 用户态可访问 | 演示叶项带 U；本批不模拟硬件权限检查 |
| G，bit5 | 全局映射 | 本批不接受，保持 0 |
| A/D，bit6/7 | 已访问、已修改 | 演示预先置位；本批不模拟硬件更新 |
| RSW，bit8/9 | 软件保留位 | 本批保持 0 |

`V=1` 只说明有效，不能单独判定它是叶项。本批中间项只设置 V，PPN 指向下一张表；
叶项的 R/X 至少一位置 1，PPN 指向最终数据页。W=1、R=0 属于非法组合。
Sv39 也支持在高层成为叶项的大页，本批只接受 L0 叶项，遇到高层叶项返回失败。

提供的固定数值断言是：PPN=0x12345、flags=V|R|W=7，编码必须等于 0x048d1407。

## 4. 所有权与物理页访问

`PageTable` 保存 root_ppn 和 `Vec<FrameTracker>`。Vec 持有根表和所有中间表的所有者，
PageTable 销毁时自动归还这些页，无需自行实现 Drop。

map 接收的 PPN 只是数字，**不会取得数据页的所有权**。演示中的 first、second 持有数据页，
必须在页表仍需使用这些映射期间保持存活，先 drop(table)，再 drop 数据页拥有者。
当前数字接口不能让 Rust 自动检查这条先后关系，调用方负责遵守。

read_entry/write_entry 会先在自身 frames 中找到对应拥有者，再借用其字节数组。
读取时复制出一个 PTE，写入时只修改对应的 8 字节；不会持有某个表项引用再向 Vec 追加页。
这避免了容器扩容时同时保留内部借用的问题，也避免把任意 PPN 强转成长期可变引用。

FrameTracker 新增的 bytes(&self) 提供只读借用，与已有 bytes_mut 一样，生命周期绑定拥有者。
底层直接访问物理字节仍依赖当前 Bare、页来自合法页池、独占拥有且未交给活动硬件等前提。
它没有查页表，也不代表任何 PA 在未来开启分页后都可以直接解引用。

### A：PageTableEntry::new

把 ppn.as_usize() 转成 u64，左移 10 位后与 flags 合并，构造 Self。
调用者已保证 flags 合法；中间项传 V，叶项传经验证的权限再加 V。

### B：PageTableEntry::ppn

将 bits 右移 10，再用 PPN_MASK 保留 44 位，转为 usize 后构造 PhysPageNum。
掩码保证数值满足类型范围，可以用 expect 说明这是内部不变量。

### C：PageTable::map

按顺序完成：

1. validate_leaf_flags(flags)?，非法权限必须在修改页表前返回 Err。
2. 调用 ensure_leaf_table(vpn)? 取得最终 L0 表页的 PPN。
3. 取 vpn.indexes()[2]，用 read_entry 读取最终表项。
4. 如果原项有效，返回 Err，不能覆盖原映射。
5. 构造带 flags | PTE_V 的新表项，调用 write_entry，返回其 Result。

map 的输入为页号，所以没有页内偏移。它不清零或释放数据页，也不分配数据页。

### D：PageTable::translate_va

从 va.floor().indexes() 得到索引，table 从 root_ppn 开始。
按根到叶遍历三个索引，每一步 read_entry(...).ok()?，再检查 V。

- 遍历深度 0/1 对应硬件 L2/L1：要求 flags 恰为 PTE_V，然后跟随 entry.ppn()。
- 遍历深度 2 对应硬件 L0：要求叶项，并拒绝 W=1、R=0。
  将 entry.ppn().to_addr().as_usize() 与 va.page_offset() 相加，再构造 PhysAddr 返回。
- 缺失、表页不归自己所有、遇到本批不支持的结构，返回 None；遍历未找到叶项也返回 None。

PhysAddr::new 本身返回 Option，可以作为成功分支的返回值。
页首低 12 位为 0，offset 小于 4096，合法 56 位 PA 页号与偏移相加不会越界。
此函数只计算地址，不分配页，也不直接解引用输入 VA。

## 6. 已提供的中间表分配路径

ensure_leaf_table 从根表查前两级。已有 V-only 中间项就继续跟随；缺失时，
先为 Vec 预留容量，再把这条路径需要的全部中间页分配到局部 pending 数组，
全部成功后才依次写入父表项并将拥有者移进 frames。

如果分配失败，尚未发布的局部拥有者会自动 Drop，已分配的临时页归还。
整个过程不持有页分配器锁销毁 Tracker。Vec 的容量可能已增长，
因此不承诺所有失败都让堆字节统计完全不变；页帧不会因此泄漏。

重复映射一定已经有完整路径，因此拒绝该请求不应分配新表页或改变原叶项。
查询使用 read_entry 遍历，不能调用 ensure_leaf_table，否则“查看”也会分配页。

## 9. 理解题与答案审查（2026-10-19）

以下保留作者原答，逐题记录审查与修正版。补充讲解不记作作者已独立答对。

### 第1题：两种移位与有效表项

问题：为什么 PTE 编码用 PPN 左移 10，而物理页首地址用左移 12？只看到 V=1 能判断是叶项吗？

**作者原答：**

> 物理页要4kb对齐，而PTE只是把几个flags特权位抓回来，PTE_V = 1代表的是当前指向存在，不直接代表叶

**审查：** 页对齐和 V 不等于叶项的方向正确。还需明确左移量来自两种不同布局，
且 PTE 低10位不全是特权位；V 表示该表项有效，不保证物理目标或完整后续路径必然可用。

**修正版：**

物理页大小为4096字节，页首地址低12位为0，因此 PPN << 12 得到物理页首地址。
PTE 则把 PPN 存在 bits[53:10]，编码用 PPN << 10；低8位为 flags，bit8/9 为软件保留位 RSW。
两者分别是物理地址布局与表项布局，不能混用。

V=1 表示表项有效，仍需查看 R/X：本批中间项只带 V，指向下一级表；
叶项至少有 R 或 X，且 W=1 必须同时有 R。不能仅凭 V 判断叶项。

### 第2题：三级查询、偏移与共享表页

问题：0x40001234 的索引为 [1,0,1]。请追踪根表到最终 PA 的过程，说明偏移从哪里补上，
以及为什么本次两条映射需要三个表页。

**作者原答（原第二段的前半部分）：**

> vpn2=1,vpn1=0,vpn0=1，通过查询query找到相关的入口地址，再使用相应的entry.ppn()返回PPN,两条映射就能找到vpn0指向的地方了，最后一个表页才能找到物理地址

**审查：** 三个索引对应正确，已注意到末级表项给出数据页 PPN。
需要补上中间项指向下一张表、末级项指向数据页的区别，以及页内偏移和三张表共享的原因。
这里查找的是映射关系，不是程序的执行入口地址。

**修正版：**

```text
根表 L2 的第1项 → L1表的 PPN
L1表的第0项    → L0表的 PPN
L0表的第1项    → 数据页的 PPN
最终 PA = 数据页 PPN 对应的页首地址 + 0x234
```

本次第二个地址0x40002567的索引为[1,0,2]。两者前两个索引相同，所以共用根表、L1表和L0表，
只在同一张L0表中使用两个不同叶项。这就是3个表页加2个数据页，共5页。
三级表路径决定本次需要三张表，不是每条映射各占一张表。

### 第3题：数据页拥有者与 CPU 是否使用页表

问题：为什么 drop(table) 后还有两个数据页没有归还？如果 map 内接收 PPN 后立即释放对应数据页，
后续重新分配会怎样？本批软件查询成功，是否代表 CPU 已在使用新页表？

**作者原答（原第二段的后半部分）：**

> 因为不能只释放单个数据页，查询成功只代表当前没有被丢弃，而不能说已经使用

**审查：** 已区分查询成功和实际启用，但“不能只释放单个数据页”不正确。
释放哪些页由拥有者决定，查询成功表示找到有效映射，而不只是某个对象尚未被丢弃。

**修正版：**

PageTable.frames 只拥有三个页表页，drop(table) 因此只归还这三页。
两个数据页分别由 first、second 持有，等它们各自销毁时才归还。
数据页可以单独释放，但只要还需要通过映射使用该页，就必须保留它的拥有者。

map 只记录 PPN，不取得数据页所有权。如果过早归还数据页，分配器可能把它交给新拥有者，
旧映射仍指向同一个 PPN，后续使用就可能访问或破坏新拥有者的数据。

软件查询成功表示沿表项找到有效映射并计算出 PA，并不表示 CPU 已启用这张页表。
本批 satp=0，CPU 仍为 Bare；软件查询与硬件启用是不同阶段。
