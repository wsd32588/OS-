## 1. 这次解决什么问题

第三章的两个应用使用不同链接地址，在Bare下由原调度器轮流运行。
B20的用户应用已有独立页表，但内核每次只能恢复同一个应用。
本批把同一个ELF装载两次：两个任务的入口、数据VA和用户栈范围相同，各自拥有不同的物理页与现场。
用户主动调用yield后，内核选择下一份现场及其用户页表继续执行。

```text
task0：write → yield ──┐
                      ↓
task1：write → yield ──┐
                      ↓
task0：从yield之后继续 → … → exit
task1：继续运行 → yield到自己 → exit
内核：全部结束 → 恢复原Bare/CSR → 回收 → 旧双应用演示
```

本批完成分页用户任务的协作调度。新路径中不启用timer抢占，也没有fork/exec或阻塞系统调用。
旧Bare双应用与第三章的`TaskContext/__switch`保留，仍在临时分页演示结束后运行。

## 2. 为什么可以由一个内核循环调度

B19/B20的汇编已经把每次用户Trap带回同一个Rust调用点：

```text
__paged_enter(ctx_va, user_token, …)
  → 保存本次内核续点
  → __paged_restore：切用户表，恢复用户寄存器，sret
  → 用户ecall
  → __paged_alltraps：保存用户现场，切公共内核表和内核栈
  → __paged_return：恢复内核续点，ret回Rust循环
```

内核处理完一个请求后，本次系统调用的内核调用链已经返回，没有尚需挂起的阻塞操作。
因此循环可以选择task1的现场和页表作为下一次`__paged_enter`的参数。
恢复的是task1自己的寄存器和sepc，task0的现场页与用户页继续保留。

这与第三章保存每个任务内核执行流的`__switch`是不同的组织方式。
本批只有一个内核循环和当前启动栈，不新增每任务内核栈，也不声称已把原调度器整体迁移到分页。
以后若在内核深处阻塞并切走，还需要为那条内核执行流安排相应续点。

## 3. 页表和资源怎样组织

| 资源 | task0 | task1 |
| --- | --- | --- |
| ELF入口 | 0x40000000 | 0x40000000 |
| 私有数据探针VA | 0x40002000 | 0x40002000 |
| 用户栈 | [0x40005000, 0x40007000) | [0x40005000, 0x40007000) |
| 用户根页表 | 独立 | 独立，token不同 |
| 用户数据物理页 | 自有 | 另一组自有页 |
| 现场槽VA | TRAMPOLINE−PAGE_SIZE | TRAMPOLINE−2×PAGE_SIZE |
| 现场页PA | 自有 | 另一个自有页 |

两张用户表共享同一物理跳板代码页，RX、U=0。
每张用户表只映射自己的现场槽，RW、U=0；公共内核表映射两个现场槽。
用户不能直接读写这些U=0页面，进入S态的跳板才使用它们。

原汇编通过参数和sscratch定位现场，没有把固定现场VA写死，因此能够原样复用。
`map_paged_context_at`只接受这两个保留槽；原`map_paged_context`仍作为单任务演示的包装。

资源总数是：

```text
公共内核表：11页
task0：5个用户表页 + 6个用户数据页 + 1个现场页 = 12页
task1：5个用户表页 + 6个用户数据页 + 1个现场页 = 12页
总计：35页
```

第二个现场槽与第一个槽处于同一个高端L0表覆盖范围，映射它不额外增加表页。
共享跳板使用已有内核代码物理页，不属于新分配的数据页。

## 4. 生命周期与任务状态

`PagedTask`持有自己的`UserImage`和现场`FrameTracker`，并复用已有`TaskStatus`枚举。
总拥有者持有公共内核空间及两个任务，字段顺序保证公共内核表先销毁；
单个任务的用户空间先销毁，随后才释放它借用映射的现场物理页。
构造失败时同样要遵守这一顺序，不能让存活的映射指向已经回收的现场页。
框架先构造尚未映射任务现场的公共内核空间，再创建两个任务；
等`PagedTasks { kernel, manager }`已接管全部资源后，才把两个现场槽映射进公共内核表。
因此第二次映射失败也会先销毁公共内核表，再销毁任务，作者不需另写这段接管逻辑。

任务状态按下面的规则变化：

| 事件 | 当前任务 | 下一任务 |
| --- | --- | --- |
| 第一次启动 | Ready → Running | 框架启动task0 |
| write或未知调用返回 | 保持Running | 继续当前任务 |
| yield | Running → Ready | 轮询找Ready，将选中者设为Running |
| exit | Running → Exited | 轮询找Ready；没有则结束本批 |

yield沿用调用号124，由新驱动识别；write64、exit93和未知调用仍复用B20分发。
yield也完成了一次ecall：必须先用B20的`prepare_resume`推进sepc、写返回值0，再调度。
exit不恢复该任务，不要求推进它的sepc；Exited任务不再成为候选。

本批保留两个任务的资源到整个演示结束，随后集中回收，避免公共内核表仍借用某个已释放的现场页。
一般操作系统可以在退出任务不再活动且所有相关映射妥善解除后单独回收它，无须等待其他任务结束。

只剩一个任务时，yield可以再次选中自己。这是合法的调度结果，不能误判为“无任务可运行”。
因此轮询范围包含当前任务作为最后一个候选。

## 5. 三处作者核心

核心集中在[os/src/mm/paged_task.rs](os/src/mm/paged_task.rs)，入口、CSR守卫、
现场Copy读写、用户示例、输出和有限调度驱动由框架提供。
框架继续调用已验收的B20分发与现场修正函数，不另写一套write。

### A：构造一个PagedTask

根据任务id取得自己的现场槽，申请现场物理页，装载用户ELF，
向用户空间映射共享跳板与自己的现场页。
用公共内核token、ELF入口和用户栈顶构造初始`PagedTrapContext`。
完成示例id初始化和现场写入后，以Ready状态返回拥有这些资源的任务。

框架会提供槽位计算及现场写入助手，相关前置条件和调用顺序写在A旁。
申请现场页应先于构造用户空间：局部变量在失败时逆序销毁，使用户表先于现场页释放。
返回对象也应保持`image`字段在`context`之前。

两个任务共享ELF文件字节，但分别装载、分配数据页；不能复制一个拥有者代替第二次装载。
初始现场只构造一次，后续yield恢复时不重新初始化用户寄存器或ELF。

### B：find_next_ready

从当前任务的下一个位置开始环形扫描，共检查TASK_COUNT个候选。
候选下标为`(current + offset) % TASK_COUNT`，offset范围是`1..=TASK_COUNT`。
遇到Ready就返回该下标；全部检查后仍没有则返回None。

只检查Ready，不能因为槽位存在就选中Running或Exited。
最后一次会检查当前任务本身：C在yield时已把它设回Ready，因而可以合法选中。

### C：schedule_after_trap

1. 检查当前任务确实为Running，这是内核状态不变量。
2. 根据Yield/Exit原因，把它改为Ready或Exited。
3. 调用B查找下一任务。
4. 找到则将选中任务改为Running，更新current，返回`Some((原下标, 新下标))`；没有则返回None。

状态必须先更新再查找。不能把退出任务重新设成Ready，也不能先选任务再处理当前状态。
这里仅决定“下一次运行谁”，真正写回现场、进入汇编和切用户表由驱动完成。

三处完成后移除本文件的`compile_error!`守卫，再集中构建运行。

## 6. 用户示例与固定P0

同一个`task_demo` ELF装载两次，`.data.probe`首字节由内核分别写入0/1作为任务id，
第二字节作为私有计数器。不能只把id塞进初始a0：当前用户`_start`不会保证把它传给零参数main。
id放在data而不是BSS中，避免用户启动清BSS时将它抹除。

task0执行两轮，task1执行三轮。每轮写入不同的私有计数值，输出任务标签，再yield，
恢复后检查返回值和原计数。task0另外调用一次未知系统调用，并检查-1后继续。
最终两个main均返回0，由既有用户运行库调用exit。

P0由协作者承担，范围在本批固定：

- 正常路径：同VA不同PA，两个任务交替yield，私有计数跨切换保留，分别exit(0)。
- 正常收尾：task0退出后，task1仍能yield到自己，Exited任务不会再运行。
- 唯一拒绝：一次未知调用返回-1，随后该任务继续运行；本批不重复B20的缓冲区拒绝矩阵。
- 核心不变量：5次write、5次yield、2次exit、1次未知调用，共13次U ecall；
  11次普通调用后恢复，另有两个任务各自的首次进入。
  两张用户根不同、现场页不同、跳板PA相同，用户表不映射对方现场槽，公共内核表映射两者。
  每轮保持35页及堆用量不增长；最后恢复原8项CSR/Bare，再完整回收，free=3008、in_use=0。
- 同次启动保留已有B14—20标记和旧Bare双应用运行，正常关机退出0。

“11次恢复”只统计已经处理普通调用后的再次进入；若统计本批所有`sret`，还要加两个首次进入，共13次。
驱动最多接收13次Trap，超出即报错，避免错误现场形成无限ecall循环。

P2可选：更多任务数、抢占、阻塞或动态创建，属于后续扩展，不是本批作业或完成前提。

## 7. 完成后的三个理解题

1. 两个任务使用相同ELF入口、数据VA和用户栈VA，为什么仍能各自保留计数？切换时到底换了哪些东西？
2. yield为什么先将当前任务改回Ready，而exit必须标为Exited？轮询为何包含自己，write为何不必触发调度？
3. 本批为何可以复用同一个内核循环，不调用第三章的`__switch`？35页由哪些所有者保活，为什么本批安排在全部任务结束后集中回收？

### 原回答、集中审查与修正版（2026-10-25）

**第1题原答：**

> . = USER_BASE_ADDRESS;
> .text : {
>     KEEP(*(.text.entry))
>     *(.text .text.*)
> }
>
> 这个吧，入口的时候用户va是和数据va一个位置开始的，但是到了真实运行的阶段，我们对数据与用户栈处理不是相同的逻辑，切换的时候实际上只是切换了指向的栈地址

**审查：**链接脚本规定虚拟布局，但不是隔离的原因。“两个任务的入口/数据/栈VA相同”
是分别比较task0和task1对应区域，不是说同一个任务的代码、数据和栈从同一地址开始。
实际分页脚本中代码从0x40000000开始，data从0x40002000开始，栈为[0x40005000,0x40007000)。
隔离依赖各自的根页表和物理页，切换也不只改sp。

**修正版：**两个任务的虚拟布局相同，但它们各自的页表把相同VA映射到不同PA，
因此数据和用户栈可以分别保留。内核选择下一任务后，向恢复入口传入它的现场槽与用户token；
恢复汇编切换satp并同步地址翻译，恢复该任务的完整用户整数寄存器、sstatus和sepc，最后sret。
用户sp只是其中的x2；代码/数据物理页一直保留，不因这次调度而复制或重新装载。

**第2题原答：**

> Yield是主动让出，之后还要使用，但是Exit是退出不再使用，如果只剩下自己，也要遵循使用规范啊，不然不返回自己那么也就不再yield，那么下一个进来的进程也无法正常运行了

**审查：**正确区分了主动让出与退出。选回自己的直接原因是当前任务仍可运行，
不是为将来新进程到来保留条件；本批只有两个固定任务，没有动态创建新进程。

**修正版：**yield后当前任务还要继续，故Running→Ready；exit后不再运行，故Running→Exited。
扫描只接受Ready，先检查其他任务，最后检查自己。若其他任务都已退出，自己仍为Ready，
允许选回自己即可继续执行yield之后的指令；否则会把“还有一个可运行任务”误判成没有候选。
write处理完成后可以保持当前任务Running，写回返回值并恢复，不需要强制调度其他任务。

**第3题原答：**

> 因为本次我们的目的不同，switch里是只保存需要的几个寄存器，而没有存现场页这些东西，上一个任务的现场页和数据页我们切换回来还要用

**审查：**保留现场页和数据页供恢复的理由正确，也注意到TaskContext保存的是较少寄存器。
但本批不调用__switch的关键是没有需要分别挂起的内核调用链，不是单凭保存寄存器数量不同。

**修正版：**每次用户Trap都会经__paged_return回到同一个内核事件循环，本次内核调用已经返回，
没有仍需挂起的阻塞调用链，所以循环可以直接选择另一份用户现场和根表，不需要切换一条任务专属内核调用链。
第三章的__switch保存内核函数调用续点，完整用户现场由Trap入口另行保存，两者职责不同。
35页由公共内核MemorySet及两个任务各自的UserImage/现场FrameTracker保活。
任务让出后还要恢复，其用户页和现场不能释放；本批退出任务也保留到演示结束，
待恢复原Bare/CSR并同步后，先销毁公共内核表、再各用户表和现场页，避免共享内核表仍借用已释放现场。
按任务退出逐个回收需要先妥善解除相关映射，并非一般系统都必须等全部任务结束。

三题已集中讲解。修正版含协作者补充，不将补充部分计作原答已经独立覆盖；
